## Exa investigation

Discovery and follow-up retrieval used Exa through Executor, with Firecrawl used to retrieve Bun's documentation entry point. Searches covered Bun primitives, Pi's storage and recovery contracts, PDF.js rendering, Effect 4 worker/process APIs, Meta tool/response protocols, Baseten vision/reasoning limits, Modal lifecycle/persistence, and public drawing-evidence implementation ideas.

Older Pi search hits described a synchronous `prepare`-based facade and a proposed conservative recovery mode. Current Pi Durable documentation instead describes an asynchronous executor and recoverable built-in generation tasks. Use current package source and published exports, not an old design document or a main-branch package version, to select the installed integration.

Public drawing-review repository searches suggested useful patterns such as explicit coverage states and preserving reviewer corrections. Those are design references only. Their README claims are not evidence of engineering accuracy, and no application code is proposed for reuse. First-party runtime documentation and the supplied packet remain the implementation basis.

## Pi execution and storage

The current [Pi Durable README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md) describes persistent submissions keyed by `requestId`, model/tool tasks, SQLite storage, extension hooks, interrupted-tool replay declarations, and a shared storage conformance suite. The API remains experimental.

Its portable SQLite facade uses Promise-based `exec`, `run`, `get`, `all`, `transaction` and `close`. Transaction callbacks receive an exclusive transaction executor that expires after settlement. Unrelated operations queue behind the transaction. Re-entering the database object from that callback can deadlock. The [async-facade change](https://github.com/earendil-works/pi/pull/10232) explains the contract change, but the selected published package must be inspected directly.

Council follow-up retrieval of the current [Chord Node SQLite adapter](https://github.com/earendil-works/pi/blob/main/packages/chord/src/sqlite/node.ts) confirms that it serializes asynchronous transaction callbacks and directly issues transaction-control SQL. Since Moke already exercises Bun's `node:sqlite` compatibility layer for migrations/backup, the plan now tests Pi's existing adapter before authoring an Effect SQL facade. This is a sequencing choice supported by existing code, not a new claim that the adapter has passed Bun conformance. Domain SQL remains owned by Effect. The documented Node journal guarantee is WAL with `synchronous=NORMAL`; a stronger setting is a separate experiment.

Pi storage expects one owning process; it does not supply cross-process ownership fencing. Its documented Node SQLite adapter uses WAL with `synchronous=NORMAL`, which differs from a stronger power-loss target. Domain and Pi journal databases are not one atomic transaction. Stable operation receipts must reconcile that boundary.

Pi's `beforeRequest` hook adjusts messages. Hooks are not a reliable enforcement boundary because hook errors can be reported and skipped. The implementation must prove that a provider wrapper can block automatic paid-call reissue, retries and compaction until the attempt ledger permits dispatch. This remains a go/no-go question, not a verified integration feature.

Follow-up retrieval of Pi's [generation task](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/generation.ts), [Responses adapter](https://github.com/earendil-works/pi/blob/main/packages/ai/src/api/openai-responses.ts), and [provider retry helper](https://github.com/earendil-works/pi/blob/main/packages/ai/src/utils/provider-retry.ts) distinguishes conversation `sessionId` from durable generation identity and identifies a possible inner HTTP retry layer. Set retries explicitly to zero and measure actual transport sends. Disable automatic compaction in the first bounded core until its request identity can satisfy the same policy.

The generation source checks `toolExecution === "sequential"`; the plan uses that actual setting rather than a reviewer's shorthand `serial`. Pi's interrupted-tool recovery requires an explicit `replay: "safe"` declaration. Operation receipts alone do not cause replay, and declaring replay safe does not make an uncertain paid SAM request safe to resend.

Pi's README also distinguishes detaching a wait, aborting a conversation and closing the harness. A close can wait on uncooperative task code. Moke's existing `desktop/backend.ts` grants the backend three seconds before forced termination, so graceful drain is bounded and forced termination must preserve uncertainty rather than promise every receipt was committed.

The existing [Pi AI providers](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md) are the first adapter candidates. Meta's credential naming differs from Moke's configuration, and the organizer Baseten model ID must be passed explicitly. No paid model probe was run during planning.

## SQLite connection and ownership checks

SQLite's [foreign-key documentation](https://sqlite.org/foreignkeys.html) requires runtime enforcement per connection and notes that changing it inside a transaction has no effect. The matching Effect Bun driver initializes WAL and busy timeout but does not explicitly initialize foreign keys. The planned connection initializer must set and verify enforcement before a transaction and apply its selected connection-local durability settings.

The [SQLite locking protocol](https://sqlite.org/lockingv3.html) documents exclusive writer reservation and failure of a competing writer. This supports a dedicated local ownership-lock database as a candidate backend process guard. The plan deliberately separates that lifetime-scoped lock resource from short application transactions, excludes it from restore, and requires a two-process/crash test on each supported local filesystem. It is not a distributed lease or cloud fencing mechanism. A process-local registry and Electron's single-instance lock do not protect an independently launched backend.

## PDF rendering

Mozilla's [PDF-to-PNG example](https://github.com/mozilla/pdf.js/blob/master/examples/node/pdf2png/pdf2png.mjs) demonstrates `getDocument`, a viewport, the document's canvas factory, page rendering, PNG output and cleanup. It also configures CMaps and standard fonts. Its [canvas replacement](https://github.com/mozilla/pdf.js/pull/19015) moved the Node path to `@napi-rs/canvas`.

This supports PDF.js as the first rendering candidate. It does not establish Bun compatibility, region-only rendering memory use, native-addon packaging or cancellation behavior. Test those with the installed versions, representative drawings and the compiled backend. Preserve original PDF coordinates rather than relying on a reduced overview for measurements.

Council follow-up searches found a current [Mozilla packaging update](https://github.com/mozilla/pdf.js/commit/bc38b633eefc6d005f54ad921ab36f8f4d2efc19) that already lists `@napi-rs/canvas` as the distribution's optional dependency. An old `pdfjs-dist` GitHub master snapshot still describes version 3.2.146 with `canvas`; it cannot establish today's published dependency requirements. Inspect the exact selected npm package before considering an override. A blanket `canvas` alias is not a required first step. Bun's own [native-addon compilation tests](https://github.com/oven-sh/bun/blob/88417471/test/napi/napi.test.ts) show general compiled addon support, not proof that Moke's PDF package works.

## Provider capability boundaries

- [Meta Responses](https://dev.meta.ai/docs/protocols/responses) and [tool calling](https://dev.meta.ai/docs/tool-calling) document image inputs, tool-result continuation, response identity and background work. The actual Pi adapter must preserve the chosen context protocol and permit attempt admission. Background request creation has a documented 1 MiB body limit and cannot be combined with initial response streaming; file references and later stream retrieval are separate capabilities.
- [Meta protocol selection](https://dev.meta.ai/docs/protocols) distinguishes Responses reasoning continuity from Chat Completions. Opaque state needed for continuation is different from displaying or logging private reasoning.
- [Baseten Model APIs](https://docs.baseten.co/inference/model-apis/overview) currently states that Muse Spark Open does not support structured outputs or JSON mode. Tool calling and application-side Schema validation are the starting path. Do not send unsupported strict-output options simply because the route is OpenAI-compatible.
- [Baseten vision](https://docs.baseten.co/inference/model-apis/vision) and [reasoning](https://docs.baseten.co/inference/model-apis/reasoning) describe model-dependent capabilities. Public examples use a different Spark Open slug from the organizer's `meta-models/muse-spark-open-1026`. Test the exact granted route; public catalog behavior does not establish that grant's support or quota.
- [Meta segmentation](https://dev.meta.ai/docs/media-segmentation) remains a separate adapter investigation. A successful text or image-and-tool turn does not verify mask decoding or physical measurement.

Exa follow-up search and retrieval of [SAM prompting](https://dev.meta.ai/docs/sam/segmenting), [output grammar](https://dev.meta.ai/docs/sam/reading-segmentation) and [client libraries](https://dev.meta.ai/docs/sam/client-libraries) confirms pixel-coordinate boxes with inclusive maximum edges and media width/height after display orientation. Mask raster dimensions can differ from the submitted image dimensions. Pin and use the official `@meta-sam/parser`; its version must support the chosen confidence-bearing output and encoding. Preserve the full transform to PDF coordinates.

The matching Effect source states that `Schema.toJsonSchemaDocument` emits draft 2020-12 for the canonical JSON codec. Its default excess-property behavior and codec transformations can differ from naive decoding of the domain schema. The plan requires a supported tool subset and comparison cases before descriptor conversion; schema generation cannot replace application-side decoding.

## Modal limits and handoff implications

The official [Sandbox guide](https://modal.com/docs/guide/sandboxes), [filesystem guide](https://modal.com/docs/guide/sandbox-files), [snapshot guide](https://modal.com/docs/guide/sandbox-snapshots), [exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots), [networking](https://modal.com/docs/guide/sandbox-networking), [JavaScript SDK](https://modal.com/docs/sdk/js/latest) and [Dict guide](https://modal.com/docs/guide/dicts) were investigated through Exa.

Sandbox lifetimes are finite and must be configured. Filesystem snapshots exclude mounted Volumes. Volume commit/reload behavior is explicit; a best-effort exit snapshot is not the sole durable checkpoint strategy. Authenticated Sandbox access exists, but a tunnel or connect token does not define application authorization. SDK parity must be checked for the exact selected features.

The checked sources do not establish a transactionally fenced owner ledger for Moke. A shared Volume or Dict is therefore not assumed to be a lease/CAS coordinator. The first plan uses a conservative one-way handoff with durable local relinquishment and one bound Sandbox; automatic takeover requires a separate design. No cloud resources were created during this investigation.
