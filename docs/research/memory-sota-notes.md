# Long-term memory for LLM agents: state of the art (October 2026)

Research date: October 30, 2026. Status: literature and product survey. This note informs a later MOKE memory design; it proposes no design itself.

Question: what does the field know, with evidence, about agent memory that learns an organization's practices and resurfaces prior work, and which of the evidence transfers to firm-scoped review of engineering drawing PDFs?

Evidence labels:

- **[measured]**: an experiment with a stated protocol. The authors may still be the vendor.
- **[vendor claim]**: a self-reported product number or a capability statement without an independent protocol.
- **[inference]**: my reading of the evidence.

Dates are publication or last-revision dates. Undated documentation was read on 2026-10-30. arXiv identifiers encode the submission month (`2605.x` means May 2026).

Repository context: Bun 1.4.4 (`.bun-version`), `effect` 4.0.4 and `@effect/sql-sqlite-bun` 4.0.4 (`package.json`).

## 1. Memory architectures and products

### Mem0

**2025 paper** (arXiv 2504.19413, 2025-04-28): https://arxiv.org/abs/2504.19413

- **Write path.** An LLM (GPT-4o-mini in the paper) extracts candidate facts from a new exchange. It sees a rolling summary plus the last m=10 messages. Each candidate is then compared with the s=10 most similar stored memories, and the LLM chooses one of four operations: `ADD`, `UPDATE` (augment), `DELETE` (contradicted) or `NOOP`.
- **Graph variant (Mem0g).** It extracts entity and relation triplets. A conflict resolver _marks relations invalid rather than deleting them_.
- **Retrieval.** Mem0 uses vector similarity. Mem0g adds entity-anchored subgraph expansion and triplet semantic matching.
- **LoCoMo results** (J = LLM-as-judge accuracy) [measured, vendor-run]:

  | System                     | Overall J | p95 total latency | Notes                  |
  | -------------------------- | --------- | ----------------- | ---------------------- |
  | Full context (~26k tokens) | 72.90     | 17.1 s            |                        |
  | Mem0g                      | 68.44     | 2.59 s            |                        |
  | Mem0                       | 66.88     | 1.44 s            | ~1.8k retrieved tokens |
  | Zep                        | 65.99     | 2.93 s            |                        |
  | Best RAG                   | ~61       |                   |                        |
  | LangMem                    | 58.10     | 60 s              |                        |
  | OpenAI memory              | 52.90     |                   |                        |
  | A-Mem                      | 48.38     |                   |                        |

- **Store size.** Mem0 stores about 7k tokens per conversation and Mem0g about 14k. The paper puts Zep's graph above 600k tokens.
- **Takeaway.** Even in the vendor's own run, full context beat every memory system on accuracy. Memory won on latency and cost.

**Dispute.** Zep re-ran the benchmark and reported a corrected Zep score of **75.14 ±0.17 J** (blog, 2025-05-06): https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/. Mem0 disputed the setup in an undated GitHub issue that claims 58.44%: https://github.com/getzep/zep-papers/issues/5. [vendor claims both ways]

**April 2026 algorithm** (blog 2026-04-16, updated 2026-09-28): https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm

- **Extraction.** Mem0 abandoned two-pass `ADD/UPDATE/DELETE` reconciliation for **single-pass, ADD-only extraction**: "overwrites sometimes erased key information … deletes sometimes removed information that would be relevant later"; new facts now live alongside old ones. Mem0 says this roughly halved extraction latency.
- **Agent facts.** Facts generated by the agent, such as "I booked X", are now stored as first-class memories.
- **Retrieval.** Semantic, keyword (with verb normalization) and entity scores are computed in parallel and fused by rank.
- **Reported results** [vendor claim]:

  | Benchmark   | Old algorithm | New algorithm |
  | ----------- | ------------- | ------------- |
  | LoCoMo      | 71.4          | 92.5          |
  | LongMemEval | 67.8          | 94.4          |
  | BEAM-1M     | n/a           | 64.1          |
  | BEAM-10M    | n/a           | 48.6          |

  Each query uses about 7k tokens.

- **Survey and pricing.** Mem0's own survey of the field: https://mem0.ai/blog/state-of-ai-agent-memory-2026 (2026-04-01, updated 2026-10-10). The pricing page lists graph memory, user profiles and "Dream (memory consolidation)" only on custom plans: https://mem0.ai/pricing.

**Independent check.** Under a matched gpt-4.1-mini answer model, another group measured LoCoMo at **61.4% for Mem0**, 65.4% for Supermemory and about 71% for Zep (arXiv 2605.04897, 2026-05-06): https://arxiv.org/abs/2605.04897 [measured, competitor-run]

### Zep / Graphiti

Zep paper, arXiv 2501.13956 (2025-01-20): https://arxiv.org/abs/2501.13956

**Graph structure.** Graphiti builds a three-tier graph: an episode subgraph (raw messages and documents, non-lossy), a semantic entity subgraph (entities and fact edges) and a community subgraph (label-propagation clusters with summaries).

**Bi-temporal edges.** Each edge carries `t_valid`/`t_invalid`, when the fact held in the world, and `t'_created`/`t'_expired`, when the system recorded or retired it.

**Contradictions.** An LLM compares a new edge with semantically related edges. When it finds an overlapping contradiction, it sets the old edge's `t_invalid` to the new edge's `t_valid`. The old fact is invalidated, not deleted.

**Retrieval.** Cosine similarity, BM25 and breadth-first graph search, followed by rerankers: RRF, MMR, episode-mentions, node-distance or a cross-encoder.

**Results** [measured, vendor-run]:

- Deep Memory Retrieval: 94.8% vs MemGPT 93.4%. The authors call DMR too small: 60-message conversations that fit in context.
- LongMemEval_s (~115k-token histories):

  | Answer model | Full context | Zep   | Latency (full → Zep) | Prompt tokens with Zep |
  | ------------ | ------------ | ----- | -------------------- | ---------------------- |
  | gpt-4o       | 60.2%        | 71.2% | 28.9 s → 2.58 s      | ~1.6k                  |
  | gpt-4o-mini  | 55.4%        | 63.8% | not extracted        | ~1.6k                  |

**Status and cost.**

- Graphiti is open source. A 2026-06-08 commit brought its MCP server to "core-parity" for bi-temporal queries, sagas, communities and custom types: https://github.com/getzep/graphiti/commit/29a756595e3a00a7511b8e82d2593d6a0a587e61
- Zep Cloud bills 1 credit per Episode up to 350 bytes. Retrieval and storage are unmetered. https://www.getzep.com/pricing
- [inference] Writes are LLM-heavy: extraction, deduplication and invalidation run on every episode. The 600k-token graph figure comes from Mem0's paper, not from Zep.

### Letta / MemGPT

- **MemGPT (2023)** treats the context window as virtual memory. Core memory blocks are labelled, size-limited text that the agent edits through tools. Recall memory is searchable conversation history. Archival memory is a vector store the agent writes passages into. Paper: https://arxiv.org/abs/2310.08560. Memory blocks are explained at https://www.letta.com/blog/memory-blocks/ (2025-05-14).
- **Sleep-time compute** (arXiv 2504.13171, 2025-04-17; https://arxiv.org/abs/2504.13171; blog https://www.letta.com/blog/sleep-time-compute/ 2025-04-21). A background agent rewrites shared memory between tasks. Measured: about **5x less test-time compute** for equal accuracy on Stateful GSM-Symbolic and Stateful AIME; up to +13% and +18% accuracy when sleep-time compute is scaled; 2.5x lower cost per query when amortized over related queries; gains track how predictable the queries are. [measured]
- **Filesystem baseline** (blog 2025-08-12; https://www.letta.com/blog/benchmarking-ai-agent-memory/). A Letta agent on gpt-4o-mini reached **74.0% on LoCoMo** with conversation history stored in plain files and searched by the agent, without specialized memory tooling. Letta argues the result says more about how well agents use search tools than about specialized memory mechanisms. [measured, vendor-run]
- **Context Repositories and MemFS** (blog 2026-02-12; https://www.letta.com/blog/context-repositories/; docs https://docs.letta.com/concepts/memfs/index.md). Letta Code memory is now a **git-backed file tree**. Every memory change is a commit; subagents learn in isolated worktrees and merge through git conflict resolution, so several reflection agents can write at once; `/doctor` audits duplication and token use. The older sleep-time docs now redirect to MemFS: https://docs.letta.com/guides/agents/architectures/sleeptime.

### LangMem (LangChain)

Source: https://langchain-ai.github.io/langmem/concepts/conceptual_guide/

- **Memory types.** Semantic (a schema'd profile or an unbounded fact collection), episodic (past experiences as few-shot examples or summaries) and procedural (prompt rules updated by a prompt optimizer).
- **Writes.** Memories form "in the hot path" through agent tools, or in the background through a debounced reflection executor. `create_memory_store_manager` defaults to `enable_deletes=False`.
- **Measured result.** In Mem0's LoCoMo run, LangMem had the highest search latency of any system (p95 ~60 s). [measured, competitor-run]

### A-MEM

A-Mem (arXiv 2502.12110, NeurIPS 2025): https://arxiv.org/abs/2502.12110

- **Write path.** Zettelkasten-style notes. On insert, the LLM generates context, keywords and tags, links the note to similar historical notes, and can rewrite their attributes ("memory evolution").
- **Measured result.** A-Mem scored 48.38 J in Mem0's LoCoMo run. [measured, competitor-run]
- [inference] Rewriting old notes on insert is the same context-collapse risk that ACE describes (section 2).

### MemOS (MemTensor)

Papers: arXiv 2505.22101 (2025-05-28) and 2507.03724 (v4 2025-12-03). https://arxiv.org/abs/2507.03724

- **Units.** The MemCube unit wraps three kinds of memory: plaintext, activation (KV-cache) and parameter (LoRA). Each carries provenance and version metadata. It is scheduled like an operating-system resource.
- **Claimed results.** MemOS claims first place on LoCoMo, LongMemEval, PreFEval and PersonaMem against MIRIX, Mem0, Zep, Memobase, MemU and Supermemory. [vendor claim]
- **Related benchmark.** MemTensor authors also built HaluMem (section 3), where MemOS ranks first. That is a conflict of interest worth noting.

### Cognee

Docs: https://docs.cognee.ai/python-api

- **Pipeline.** `add` → `cognify` (chunk, LLM-extract a knowledge graph and embed) → `search`. It stores relational, vector and graph data together. `memify` is deprecated in favour of `improve()` (https://docs.cognee.ai/core-concepts/main-operations/legacy-operations/memify).
- **Paper** (arXiv 2505.24478, 2025-05-30; https://arxiv.org/abs/2505.24478). Systematic hyperparameter tuning of chunking, graph construction, retrieval and prompts on HotPotQA, TwoWikiMultiHop and MuSiQue gave "consistent but not uniform" gains. The authors stress that the evaluation metrics are unreliable. [measured, vendor-run]

### HippoRAG 2

HippoRAG 2 (arXiv 2502.14802, ICML 2025): https://arxiv.org/abs/2502.14802

- **Method.** It builds an open knowledge graph from passages and retrieves with Personalized PageRank over a combined passage and phrase graph, with an LLM filtering recognition.
- **Results.** About **+7% on associative (multi-hop) memory** tasks over the best embedding retriever, while staying at or above dense RAG on simple factual recall. Earlier graph RAG methods had fallen below dense RAG on factual recall. [measured]

### GraphRAG, LazyGraphRAG and LightRAG

- **LazyGraphRAG** (Microsoft Research blog, 2024-11-25; https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/). Full GraphRAG indexing with community summaries is expensive; LazyGraphRAG's indexing cost equals vector RAG's and is **0.1% of GraphRAG's**, and it matches GraphRAG Global Search quality at **more than 700x lower query cost**. [measured, vendor-run]
- **LightRAG** (arXiv 2410.05779; EMNLP Findings 2025; https://arxiv.org/abs/2410.05779). Dual-level (entity and theme) graph plus vector retrieval, with incremental graph updates.
- **Independent comparison** (arXiv 2502.11371, v3 2026-03-04; https://arxiv.org/html/2502.11371v3). RAG and GraphRAG are complementary, with no consistent winner: RAG wins on single-hop, detail-oriented questions and GraphRAG on multi-hop questions. Community-summary search loses query-specific detail, LLM-judge comparisons of summaries show strong position bias, and GraphRAG costs more to build, has higher latency and a larger footprint, and is sensitive to graph quality. [measured]

### Supermemory

- **Data model** (https://supermemory.ai/docs/concepts/graph-memory). Raw documents are the source of truth for RAG, and extracted "memories" are a derived fact graph. Edges are typed as _updates_, _extends_ or _derives_ (blog 2026-07-23; https://supermemory.ai/blog/memory-graph-relationship-semantics/).
- **Consolidation.** An asynchronous "dreaming" step builds the graph from documents (https://github.com/supermemoryai/supermemory/blob/main/apps/docs/concepts/how-it-works.mdx).
- **Claim.** LongMemEval-S **Recall@20 = 97%** (report May 2026; https://supermemory.ai/research/longmembench/). [vendor claim] That figure is retrieval recall, not QA accuracy. An independent matched run measured 65.4% LoCoMo QA (arXiv 2605.04897), and HaluMem measured a 16.4% correct-update rate.

### Notable 2025–2026 entrants (all self-reported)

- **Hindsight** (Vectorize; arXiv 2512.12818, Dec 2025; ACL 2026 demo; https://arxiv.org/abs/2512.12818). Memory is split into four networks (world facts, agent experiences, synthesized entity observations, evolving opinions or beliefs) behind `retain`, `recall` and `reflect`, because existing systems "blur the line between evidence and inference". An open 20B backbone rose from 39% (full context) to 83.6%; larger backbones reached 91.4% on LongMemEval and 89.61% on LoCoMo. The product site claims LongMemEval-S 94.6% and BEAM-10M 64.1% (https://hindsight.vectorize.io/).
- **EverMemOS** (arXiv 2601.02163, ACL 2026; https://arxiv.org/abs/2601.02163). A self-organizing memory OS. A third party reports 94.5% on LoCoMo with a GPU embedder and Neo4j (arXiv 2605.04897).
- **True Memory / "Storage Is Not Memory"** (Sauron Labs, arXiv 2605.04897, 2026-05-06). Argues that "extraction at ingestion is the wrong primitive" because content discarded before the query is known cannot be recovered. It keeps events verbatim and puts the work into a multi-stage retrieval pipeline in **a single SQLite file on CPU**, with no vector or graph database. Results: LoCoMo 93.0% (semantic-match judge, more lenient than strict scoring), LongMemEval 87.8%, BEAM-1M 76.6%; a 56-configuration ablation spanned only 1.3 points.
- **Agent Zero Memory** (arXiv 2608.29606, Aug 2026; https://arxiv.org/abs/2608.29606). Three parallel views of one history: an episodic event timeline, an entity–event graph, and a curated, **citation-locked** hierarchy of durable facts that abstains when no citation exists. It reports 95.60% LongMemEval and 93.60% LoCoMo; across eight backbones, accuracy varied 3.4 points while cost per query varied about 30x.
- Others seen but not evaluated here: MAGMA multi-graph memory (arXiv 2601.03236, 2026-01-06), MIRIX, Memobase, MemU, ZenBrain.

### Cross-cutting pattern (2025 → 2026)

[inference, supported by the sources above] The field is moving away from destructive, extract-and-overwrite memory and toward three practices:

- **Keep raw episodes immutable.** Zep's episode subgraph, Mem0's 2026 ADD-only change, True Memory's verbatim events, Supermemory's documents as source of truth, and Letta's git history all do this.
- **Derive views that can be rebuilt.** Facts, entities, summaries and playbooks are derived from those episodes and carry links back to them.
- **Retrieve with several signals fused.** Lexical, semantic, entity, temporal and graph signals are combined, then reranked.

Consolidation increasingly runs asynchronously: Letta sleep-time agents, Mem0 "Dream" and Supermemory "dreaming".

### Failure modes with evidence

- **Context collapse** (ACE, §2). Monolithic LLM rewriting of an accumulated context can erase it. In ACE's Dynamic Cheatsheet run, the context went from 18,282 tokens (66.7% accuracy) to **122 tokens (57.1%)** in one step, below the no-memory baseline of 63.7%. ACE's countermeasure is localized delta edits plus deterministic merge and deduplication ("grow-and-refine"); Mem0's 2026 move to ADD-only writes addresses the same failure. [measured]
- **Brevity bias** (ACE). Optimizers that favour concise prompts drop the domain-specific detail that made them work. [measured, qualitative]
- **Experience-following and error propagation** (arXiv 2505.16067, May 2025; ACL 2026; https://arxiv.org/abs/2505.16067). When a retrieved memory's input is similar to the current task, the agent's output closely copies it, so wrong stored experiences compound, and "misaligned experience replay" means even seemingly correct records can mislead. Gating additions on evaluator quality, and using later task evaluations as free quality labels, mitigates both. [measured]
- **Raw versus distilled memory.** The evidence conflicts:
  - **Distilled wins:** ReasoningBank's distilled strategies beat raw trajectories and AWM. AWM _degrades_ on WebArena's cross-website subset. Abstract procedural memories transfer more reliably than detailed trajectories (arXiv 2604.27003, Apr 2026).
  - **Raw wins:** SkillEvolBench (arXiv 2605.24117, May 2026; https://arxiv.org/abs/2605.24117) finds that agents "rarely form robust reusable skills". Raw-trajectory reuse often beats distilled skills, and writing more skills adds "episode-specific drift and procedural clutter".
  - **Narrow sources overfit:** AFTER finds that skills evolved from narrow experience overfit their source context.
  - [measured] The disagreement is unresolved.
- **Interference and forgetting** (arXiv 2604.27003; https://arxiv.org/html/2604.27003). External memory "does not resolve the continual-learning problem; it reshapes it". Old and new experiences compete for retrieval, negative transfer hurts the hard cases most, and finer-grained organization can cause severe forgetting. [measured, ALFWorld and BabyAI]
- **Hallucinated writes.** HaluMem (section 3) shows that errors come mostly from extraction and updating, then propagate into answers.
- **Poisoning.** Covered in section 6. Self-generated memories are the attack surface in MINJA and MemoryGraft.

### Anthropic and OpenAI first-party features

- **Anthropic memory tool and context editing** (2025-09-29; https://www.anthropic.com/news/context-management; docs https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool). The memory tool is client-side file operations under `/memories`; the application owns storage and must prevent path traversal. On an internal agentic-search evaluation, memory plus context editing scored +39% over baseline and context editing alone +29%; over 100 turns of web search, tokens fell 84%. [vendor claim]
- **Agent Skills** (2025-10-16; open standard 2025-12-18; https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills). A skill is procedural memory as a folder holding `SKILL.md`, scripts and resources. Progressive disclosure keeps only the name and description in the prompt and loads the body on demand. Anthropic warns that untrusted skills can exfiltrate data.
- **Claude Managed Agents memory stores** (beta `agent-memory-2026-07-22`; https://platform.claude.com/docs/en/managed-agents/memory). Stores are file-mounted under `/mnt/memory/`, and **every change creates an immutable memory version** (an audit trail with point-in-time recovery). Access defaults to `read_write`; `read_only` is recommended for reference stores because prompt injection can write malicious memory. Limits: 10,000 memories per store, 8 stores per session.
- **Claude Code memory** (https://code.claude.com/docs/en/memory). Human-written `CLAUDE.md` rules are kept apart from agent-written "auto memory", which is typed (`user`, `feedback` for corrections, `project`, `reference`) and reviewed with `/memory`.
- **Claude app memory** (https://www.anthropic.com/news/memory): Team/Enterprise 2025-09-11, Pro/Max 2025-10-23, free plan with import from other assistants 2026-03-02 (https://www.theverge.com/ai-artificial-intelligence/887885/anthropic-claude-memory-upgrades-importing). Memory is project-scoped, with view/edit controls and incognito chats. Anthropic tested for "over-accommodation" and for reinforcing harmful patterns before launch.
- **ChatGPT memory** (https://openai.com/index/memory-and-new-controls-for-chatgpt/): saved memories 2024-02-13, "reference chat history" 2025-04-10, free tier 2025-06-03. Enterprise/Edu got improved memory with a reviewable memory summary (release notes 2026-09-29; https://help.openai.com/en/articles/10128477-chatgpt-enterprise-edu-release-notes).
- Neither vendor publishes accuracy evaluations of its consumer memory.

## 3. Benchmarks and evaluation

### What the main benchmarks measure

- **LoCoMo** (arXiv 2402.17753; ACL 2024; https://arxiv.org/abs/2402.17753). Synthetic persona dialogues of about 300 turns and 9k tokens over up to 35 sessions; the released set has 10 conversations and 1,540 scored questions (single-hop, multi-hop, temporal, open-domain).
  - **Audit** (Penfield, 2026-04-08; https://penfieldlabs.substack.com/p/we-audited-locomo-64-of-the-answer; https://github.com/dial481/locomo-audit): 99 of 1,540 golden answers (6.4%) are wrong, which caps the achievable score at **93.57%**; the standard LLM judge accepts up to 63% of intentionally wrong answers; the open-domain category (n=96) needs a difference above 15 points to be significant. [measured]
- **LongMemEval** (arXiv 2410.10813; ICLR 2025; https://arxiv.org/abs/2410.10813). 500 questions over five abilities: information extraction, multi-session reasoning, temporal reasoning, **knowledge updates**, abstention. The _S setting uses ~115k-token histories; _M is much longer. Commercial assistants dropped about 30% in accuracy over sustained interactions.
  - Design findings: decompose sessions into rounds or facts; expand index keys with extracted facts; expand queries with time-aware ranges. Penfield notes that _S fits in modern context windows.
- **MemoryAgentBench** (arXiv 2507.05257, Jul 2025; https://arxiv.org/abs/2507.05257). Four competencies fed incrementally: accurate retrieval, test-time learning, long-range understanding, selective forgetting. RAG wins on retrieval; long-context models win on learning and global understanding. **Every method scores at most 28% on multi-hop selective forgetting.** [measured]
- **BEAM** (arXiv 2510.27246, Oct 2025, v2 2026-02-21; https://arxiv.org/abs/2510.27246). 100 coherent conversations of up to **10M tokens** with 2,000 validated questions. Models with 1M-token context still degrade as conversations lengthen; the authors' LIGHT architecture (episodic + working memory + scratchpad) gains 3.5–12.7%.
- **HaluMem** (arXiv 2511.03506; EMNLP 2026; https://arxiv.org/abs/2511.03506; by MemTensor). It scores each operation separately: extraction, update and QA. [measured]

  | System      | Extraction recall | Correct-update rate |
  | ----------- | ----------------- | ------------------- |
  | MemOS       | 74.1%             | 62.1%               |
  | Zep         | not reported      | 47.3%               |
  | Mem0        | 42.9%             | 25.5%               |
  | Supermemory | 41.5%             | 16.4%               |
  | Memobase    | 14.6%             | 5.2%                |

  Update omission rates reached 74% for Mem0. QA correctness ranged 35–67%. Errors start at extraction and update, then propagate to answers.

- **Evo-Memory** (arXiv 2511.20857, Nov 2025; https://arxiv.org/abs/2511.20857). A streaming test of test-time learning across 10 datasets with more than ten memory modules. It provides an ExpRAG baseline (retrieve prior task experiences) and ReMem.
- **MemoryArena** (arXiv 2602.16313, 2026-02-18; https://arxiv.org/abs/2602.16313). Multi-session agentic tasks whose subtasks depend on each other. Agents "with near-saturated performance on existing long-context memory benchmarks like LoCoMo perform poorly" here. [measured]
- **Procedural and skill benchmarks:** AFTER (382 enterprise tasks, 22 skills; arXiv 2606.23127), SkillEvolBench (arXiv 2605.24117), SWE Context Bench (arXiv 2602.08316).

Several LoCoMo scores sit at or above the audited 93.57% ceiling, which implies lenient judging; answer models and judges differ from row to row; the same Mem0 system scores 92.5 self-reported and 61.4 in a matched third-party run. No benchmark involves images, documents as the primary memory, or organizational (multi-user) knowledge.

### Building a domain evaluation (what the literature supports)

These are evaluation methods with published precedent, not a MOKE design:

- **Score each operation separately** (HaluMem): extraction precision and recall, update correctness and omission, retrieval recall@k, then end-task accuracy. Black-box QA alone hides where errors start.
- **Replay time-ordered streams** (MemoryAgentBench, Evo-Memory): ingest chronologically and query between steps. That measures both forward transfer and forgetting of earlier knowledge (arXiv 2604.27003).
- **Include superseded facts** (LongMemEval knowledge updates, MemoryAgentBench selective forgetting) and multi-hop versions of them. This is the weakest capability measured.
- **Include abstention cases** (LongMemEval), where the correct behaviour is to suggest nothing.
- **Measure downstream task success** (MemoryArena, AFTER), not only recall: does a surfaced prior detail change a review outcome? Test cross-project and cross-reviewer transfer, as AFTER does across roles.
- **Validate the judge** (Penfield audit): seed known-wrong answers to measure judge false acceptance, hand-audit gold labels, and report Wilson confidence intervals per category. Use exact or structured checks where possible (Enginuity found token-overlap metrics under-report by 2–6x; section 4).
- **Hold the answer model fixed** across memory variants, as Agent Zero Memory and True Memory did, and report tokens and latency per query.

## 4. Multimodal and visual document memory for drawings

### Page-level visual retrievers

- **ColPali** (arXiv 2407.01449, v6 2025-02-28; https://arxiv.org/html/2407.01449).

  - Projection [inference]: 10k sheets is about 2.6 GB uncompressed.
- **ColQwen2** has dynamic resolution, capped at 768 patches: https://huggingface.co/vidore/colqwen2-v1.0
- **ViDoRe V3** (released 2025-11-05; paper arXiv 2601.08620, 2026-01; https://arxiv.org/html/2601.08620). 26k enterprise pages and 3,099 human-verified queries.
  - NDCG@10 [measured]:

    | Type   | Model                          | NDCG@10 |
    | ------ | ------------------------------ | ------- |
    | Visual | ColEmbed-3B-v2                 | 59.8    |
    | Visual | jina-v4                        | 57.6    |
    | Visual | ColNomic-7B                    | 57.4    |
    | Visual | ColQwen2.5                     | 51.9    |
    | Visual | ColPali                        | 43.1    |

API-only models:

- **voyage-multimodal-3.5** (2026-01-15; https://blog.voyageai.com/2026/01/15/voyage-multimodal-3-5/): $0.12 per M text tokens and $0.60 per B pixels (OpenRouter listing).

- **Cohere Embed 4** (2025-04-15; https://cohere.com/blog/embed-4). It beat every open model on IRPAPERS page images (R@1/5/20 = 58/87/97; arXiv 2602.17687). [measured, third party]
- **Cohere Embed 5** (2026-09-30; https://cohere.com/blog/embed-5): $0.08–0.12 per M tokens, with fused text and image input. [vendor claim]

### Reducing multi-vector storage

- **Light-ColPali token merging**: 98.2% of retrieval quality at 11.8% of the memory, and 94.6% at 2.8%. Query-agnostic pruning works poorly (arXiv 2506.04997, 2025-06; https://arxiv.org/abs/2506.04997). [measured]
- **Token pooling** at index time: factor 2 keeps about 100% of quality and halves the vectors; factor 3 keeps about 99% and cuts 66% (https://www.answer.ai/posts/colbert-pooling.html, 2024-06-27). [measured, text ColBERT]
- **Binarized MaxSim**: 32x less memory and about 4x faster scoring, with a float rerank afterwards (Vespa, 2024-09-20; https://blog.vespa.ai/scaling-colpali-to-billions/). [vendor measurement]
- **MUVERA** fixed-dimensional encodings let a single-vector index serve as the first stage for multi-vector retrieval (arXiv 2405.19504; NeurIPS 2024). [measured, text]
  - [inference] One route onto a single-vector SQLite index: MUVERA first stage, then exact MaxSim rerank of the top-k.

### Region, crop and drawing-specific evidence

- **PlanSightRAG** (state DOT standard plans; 1,898 pages and 4,056 query–page pairs; arXiv 2608.26091, 2026-08-26; https://arxiv.org/html/2608.26091). [measured]
  - R@5 by retriever:

    | Retriever            | R@5                                               |
    | -------------------- | ------------------------------------------------- |
    | Nemotron-ColEmbed-8B | 95.28%                                            |
    | ColNomic-3B          | 91.47% (91.40% zero-shot on a held-out state set) |
    | ColPali              | 76.89%                                            |
    | OCR + BGE-M3         | **36.79%**                                        |

  - LoRA fine-tuning added nothing.
  - Tiling into 400-DPI 1024 px tiles with 256 px overlap (15–30 per sheet) raised R@5 by 5.2 points and judge accuracy by 4.5 points. It also lost cross-references when a note and the detail it refers to fell in different tiles, so the authors index full pages and tiles together.
  - Failure modes: binding a dimension to the wrong component, and borrowing values from another view.
- **Blueprint** (ORNL archive of 770k engineering drawings; arXiv 2602.13345, 2026-02-12; https://arxiv.org/html/2602.13345). [measured]
  - Pipeline: detect the title block, revision table and parts list; OCR them with a VLM; normalize identifiers; fuse BM25 with dense retrieval; rerank at region level.
  - Results: +10.1 points Success@3 and +18.9% relative nDCG@3 over VLM-only retrieval, at about 9.7 s per file.
- **RegionRAG** (arXiv 2510.27261, Oct 2025): region-level retrieval gave +10.0% R@1 and +3.6% QA accuracy while using 71% of the visual tokens. **GARRET** (arXiv 2610.27829, Oct 2026): region retrieval without region labels, with 47.8% fewer vectors per page at page-retrieval parity with ColQwen2.5. [measured]
- **AECV-Bench** (floor plans; arXiv 2601.04819, 2026-01-08). VLMs reach about 0.95 on OCR-style questions, but **symbol counting is unsolved at 0.40–0.55**. The authors recommend tool-augmented, human-in-the-loop workflows. [measured]
- **MechVQA** (mechanical drawings; arXiv 2605.30794; ICML 2026). [measured]
  - Frontier VLMs score 71–77 overall; a 4B model fine-tuned with RL reaches 84.85.
  - Weakest areas: localization and multi-view consistency.
  - Typical errors: "numerically plausible but constraint-inconsistent" answers.
- **Enginuity** (parts manuals; arXiv 2606.03410): token-overlap metrics under-report capability by 2–6x compared with semantic similarity. [measured]
- **Image-to-image drawing similarity remains weak.** DeepPatent (WACV 2022) on design-patent drawings: mAP 0.29 with ImageNet features and 0.37 with patent training. A small PCB pilot measured CLIP R@10 at 0.13 against ColPali's 0.93 (https://github.com/yangchiehkang/PCB-VisualRAG; 30 queries). [measured, weak]

### Hybrid image + text retrieval

- **IRPAPERS** (arXiv 2602.17687, Feb 2026). R@1/5/20 [measured]:

  | Method                     | R@1/5/20     |
  | -------------------------- | ------------ |
  | Text hybrid (BM25 + dense) | 46/78/91     |
  | ColModernVBERT on images   | 43/78/93     |
  | Fusion of both             | **49/81/95** |

  The two modalities fail on different queries.

- [inference] Identifier and text queries (sheet numbers, title blocks, notes) favour OCR plus BM25 by region (Blueprint). Geometry and detail queries favour patch-level visual retrieval (PlanSightRAG, where OCR collapsed).
- **Commercial AEC products** advertise sheet segmentation (plan, schedule, legend, title block) and citations to bounding boxes: Bedrock (https://docs.bedrock.cv/guides/the-drawing-index) and VitruAI (https://vitruai.com/use-cases/construction-plan-archive-search/). [vendor claim, unevaluated]

## 5. Local-first implementation options (Bun, TypeScript, SQLite)

### What the repository already supports

- **Effect SQL can load extensions.** `@effect/sql-sqlite-bun` 4.0.4 exposes `loadExtension(path)` and `export` on `SqliteClient`. The module doc says "Database export and extension loading are supported; streaming queries and `updateValues` are not."
  - Source: `repos/effect/packages/sql/sqlite-bun/src/SqliteClient.ts` (lines 11, 61–71, 256–260), checked locally.
  - The client wraps one `bun:sqlite` connection behind `Semaphore.make(1)`, so an extension loaded once applies to every later query on that connection. The raw `Database` is not exposed.
- **No code uses vectors or full-text search yet.** No backend code or migration uses sqlite-vec, FTS5 or `loadExtension`.

### bun:sqlite constraints

- **macOS.** Apple's system SQLite disables extensions. Bun requires `Database.setCustomSQLite(<libsqlite3.dylib>)` before the first `Database` is created; on other OSes "SQLite is statically linked: the call does nothing and returns false" (https://bun.com/docs/runtime/sqlite, read 2026-10-30). The macOS failure message is reported in https://github.com/asg017/sqlite-vec/issues/78 (2024-08-09).
- **Compiled executables.** `bun build --compile` can embed N-API addons and assets under `/$bunfs/` (https://bun.com/docs/bundler/executables).
  - [inference, unverified] `loadExtension` calls dlopen on a real OS path, so a sqlite-vec `.dll/.so/.dylib` likely has to ship beside the executable (Electron `extraResources`) rather than inside `$bunfs`.
- **Windows locking.** The `bun:sqlite` "database is locked" issue on Windows is open (https://github.com/oven-sh/bun/issues/16119, updated 2025-11-25).
- **Bun 1.4.** The 2026-08-20 release rewrote Bun's core in Rust and fixed more than 2,900 issues (https://bun.com/blog/bun-v1.4). Older native-addon crash reports may or may not still apply.

### Vector storage options

- **sqlite-vec** (https://github.com/asg017/sqlite-vec/releases).
  - Status [vendor]:
    - Stable v0.1.9 (2026-03-31) is **brute-force KNN only**.
    - ANN (rescore, IVF, DiskANN) exists only in v0.1.10 alphas (alpha.4 2026-05-18), and alpha.2 notes that DiskANN deletes are expensive.
  - Features [vendor]:
    - `vec0` tables support metadata columns usable in KNN `WHERE` clauses.
    - **`partition key` columns** shard the index internally, which suits firm and project scoping.
    - Auxiliary columns are also supported (v0.1.6, 2024-11-20; https://alexgarcia.xyz/blog/2024/sqlite-vec-metadata-release/).
    - float32, int8 and bit vectors; `vec_quantize_binary` with Hamming distance (32x compression); Matryoshka truncation.
  - Author benchmarks (2024-08-01; https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html) [measured]: At 1M vectors, brute force takes 192 ms at 192 dims and 8.5 s at 3072 dims; binary quantization is about 10x faster with roughly 95% anecdotal recall. [inference] Corpora of 10k–100k items per firm are well within brute-force range.
  - Bun support [vendor]:
    - The JS helper `load()` supports `bun:sqlite` (https://alexgarcia.xyz/sqlite-vec/js.html).
    - Prebuilt binaries cover Windows, macOS and Linux, including the PhotoStructure fork (https://github.com/photostructure/sqlite-vec/releases, 2026-01-04).
- **FTS5 + vector hybrid in one SQL query** (Alex Garcia, 2024-10-02; https://alexgarcia.xyz/blog/2024/sqlite-vec-hybrid-search/index.html; commentary https://simonwillison.net/2024/Oct/4/hybrid-full-text-search-and-vector-search-with-sqlite/).
  - Two CTEs rank `vec0 MATCH … k=?` results by distance and FTS5 results by `rank` (negative BM25), each with `row_number()`.
  - A `FULL OUTER JOIN` on rowid combines them, scored as `Σ weight/(rrf_k + rank)` with `rrf_k = 60` (reciprocal rank fusion).
  - The post also covers keyword-first and semantic-rerank variants.
  - [inference] Check FTS5 and `FULL OUTER JOIN` (SQLite ≥3.39) in Bun's static build with `PRAGMA compile_options` and `sqlite_version()` on each target OS.
- **libSQL / Turso.**
  - libSQL has native `F32_BLOB(n)` columns, `libsql_vector_idx` and `vector_top_k()` with LM-DiskANN (2024-06-05 and 2024-07-26; https://turso.tech/blog/approximate-nearest-neighbor-search-with-diskann-in-libsql).
  - It needs `@libsql/client`, a separate native engine, not `bun:sqlite`. The PR to add a bun:sqlite backend is still open (https://github.com/tursodatabase/libsql-client-ts/pull/71, updated 2026-01-07).
  - [inference] Adopting libSQL would replace the Effect Bun client, not extend it.
  - Turso's Rust rewrite (pre-1.0) has vectors with linear scan and experimental FTS; DiskANN is an open issue (https://github.com/tursodatabase/turso/issues/832).
- **LanceDB.**
  - `@lancedb/lancedb` 0.41.0 (2026-10-29) ships native builds for Windows, macOS and Linux (https://www.npmjs.com/package/@lancedb/lancedb).
  - Multivector (ColBERT/ColPali MaxSim) columns are documented with Python examples; I did not confirm JS support (https://docs.lancedb.com/search/multivector-search).
  - Indirect Bun evidence: it runs inside a Bun single-file executable after a `createRequire` workaround (https://github.com/prosperitypirate/codexfi/issues/141, 2026-04-05).
  - It is a second storage engine beside SQLite.
- **usearch** (npm 2.25.1, 2026-04-16) offers HNSW through N-API or WASM. Its SQLite extension provides only distance functions, with no index.

## 6. Governance

### Memory poisoning and injection

- **AgentPoison** (NeurIPS 2024; arXiv 2407.12784; https://arxiv.org/abs/2407.12784): backdoor triggers in memory or RAG. Attack success above 80% at a poison rate below 0.1%, with under 1% loss on benign tasks. [measured]
- **MINJA** (arXiv 2503.03704, 2025-03; NeurIPS 2025; https://arxiv.org/abs/2503.03704). Ordinary queries trick the agent into writing malicious reasoning records itself. Injection succeeds 98.2% of the time, with 76.8% average attack success. [measured]
- **MINJA under realistic conditions** (arXiv 2601.05504, 2026-01-09). A memory bank already holding legitimate records "dramatically reduce[s]" attack effectiveness. Trust-scored sanitization helps, but its threshold needs calibration to avoid rejecting real memories. [measured]
- **MemoryGraft** (arXiv 2512.16962, 2025-12-18). Implanted fake "successful experiences" are imitated. A few poisoned records can account for a large share of retrieved experiences under lexical + embedding retrieval. [measured] This applies directly to any "prior similar work" suggestion feature.
- **Zombie Agents** (arXiv 2602.15654, 2026-03) and **WhisperBench / MemGhost** (arXiv 2607.05189, 2026-07).
  - One email payload achieved stealthy memory injection end-to-end in 87.5% of cases on OpenClaw with GPT-5.4 and 71.4% on the Claude Code SDK with Sonnet 4.6.
  - Per-session prompt filtering is insufficient. [measured, preprints]
- **Provenance laundering** (arXiv 2607.29167, 2026-07-31). LLM consolidation rewrote external observations as apparent user history, with attack success up to 1.0. [measured] [inference] Summarization and merging are trust boundaries.
- **Field reports:**
  - ChatGPT "SpAIware" persistent exfiltration via planted memories (Rehberger; https://arstechnica.com/security/2024/09/false-memories-planted-in-chatgpt-give-hacker-persistent-exfiltration-channel/, 2024-09-24)
  - Gemini delayed memory-tool invocation (https://arstechnica.com/security/2025/02/new-hack-uses-prompt-injection-to-corrupt-geminis-long-term-memory/, 2025-02-11)
  - Microsoft's "AI Recommendation Poisoning": more than 50 "remember X as a trusted source" prompts from 31 companies (https://www.microsoft.com/en-us/security/blog/2026/02/10/ai-recommendation-poisoning/, 2026-02-10)
- **MEXTRA** (ACL 2025; arXiv 2502.13172). Black-box prompts extracted more than 10–30% of stored private queries from agent memory. [measured]

### Defenses

- **Spotlighting** (arXiv 2403.14720): delimiting or datamarking untrusted text cut attack success from above 50% to below 2%. It was tested on single-turn injection, not persistent memory. [measured]
- **A-MemGuard** (arXiv 2510.02373; PMLR 2026): consensus across related memories plus a separate "lessons" memory. Attack success fell by more than 95% at minimal utility cost. [measured, author-run]
- **Platform-held provenance:**
  - PPMF (arXiv 2607.29167) authorizes a tool call only when the action's risk matches the authority of the memories behind it.
  - MemLineage (arXiv 2605.14421, 2026-05-14) uses signed entries, a Merkle log, a derivation DAG, and refusal of actions descending from external sources; it was the only configuration with 0 attack success on all three workloads. [measured, author harnesses, preprints, no replication]
- **OWASP.**
  - Agentic AI Threats and Mitigations, T1 Memory Poisoning (2025-02-17; https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/).
  - Top 10 for Agentic Applications 2026, **ASI06 Memory & Context Poisoning** (2025-12-09; https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/).
  - Recommended controls: validate writes before commit; require source attribution; expire unverified entries; weight retrieval by trust and tenancy; "prevent automatic re-ingestion of an agent's own generated outputs into trusted memory"; keep snapshots, rollback and versioning; use per-tenant namespaces; put humans in the loop for high-risk actions.
- **NIST and CSA.** NIST CAISI published agent-hijacking evaluation work (2025-01-17) and an RFI (2026-01-12). CSA MAESTRO (2025-02-06) gives threat layers. None has controls specific to memory.

### Bi-temporal validity and provenance

- **Zep/Graphiti** keeps four timestamps per edge (section 1) and invalidates contradicted edges instead of deleting them (https://arxiv.org/abs/2501.13956). Episodes stay as the lossless source. The edge-resolution code path was read from a secondary source (https://deepwiki.com/getzep/graphiti/5.3-edge-extraction-and-resolution).
- **Other systems with citations or versions:**
  - Agent Zero Memory: "citation-locked" facts that abstain without a citation.
  - MemOS: MemCube provenance and version fields.
  - Claude Managed Agents: immutable memory versions.
  - Letta: git commits.
- **W3C PROV-O** (2013-04-30; https://www.w3.org/TR/prov-o/) provides `wasDerivedFrom`, `wasAttributedTo` and related relations. [inference] No memory product checked exports PROV.

### Human approval

- **Products.**
  - Claude apps let users view and edit memory, and each project has its own (https://www.anthropic.com/news/memory).
  - Claude Code separates human rules (`CLAUDE.md`) from agent-written auto memory, which users audit with `/memory`.
  - ChatGPT has separate toggles for saved memories and chat history; deleted memories may stay in logs for up to 30 days (https://help.openai.com/en/articles/8590148-memory-in-chatgpt).
  - LangMem has no built-in approval step.
- **Evidence.**
  - A CHI 2026 interview study (n=20; https://doi.org/10.1145/3772318.3791635) found users see memory as "unforgetting" and feel privacy strain.
  - Gating memory additions on strict evaluation, including human evaluation, mitigated error propagation (arXiv 2505.16067).
  - I found **no controlled study** showing that human-approved learned rules improve downstream accuracy over unreviewed ones. [gap]

### Multi-tenant isolation

- **Mem0** scopes calls by `user_id`, `agent_id`, `app_id` and `run_id`, and filters support a `*` wildcard (https://docs.mem0.ai/platform/features/entity-scoped-memory). [inference] Isolation depends on every call carrying the right tags.
- **Zep** gives each user a graph, plus separate shared graphs (https://help.getzep.com/users-and-user-graphs).
- **Letta** documents three patterns: one agent per user, a shared agent with identities, or org-owned shared memory repositories (https://docs.letta.com/concepts/shared-memory/).
- **Incident.** Asana's MCP server exposed data across organizations (disclosed 2025-06-18; https://www.bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/). This was tenant scoping failing in an AI access layer, not in a memory product.

### Forgetting and right to delete

- **Mem0** deletes by ID, in batches of up to 1,000, or by filter; `delete_all` with no filter is rejected (https://docs.mem0.ai/api-reference/memory/delete-memories).
- **Zep** cascades a user delete as its right-to-be-forgotten path. But deleting an episode **does not regenerate** node summaries shared with other episodes, and facts it invalidated stay invalidated (https://help.getzep.com/deleting-data-from-the-graph). [vendor-documented gap] Derived summaries can keep content from a deleted source.
- **Embeddings leak text.** vec2text recovers 92% of 32-token inputs exactly (arXiv 2310.06816, EMNLP 2023), and ZSInvert (arXiv 2504.00147, 2025) works zero-shot on any encoder. [measured] Vectors need the same deletion and access rules as their source text.
- **GDPR.** EDPB Opinion 28/2024 (2024-12-17; https://www.edpb.europa.eu/system/files/2024-12/edpb_opinion_202428_ai-models_en.pdf) decides anonymity case by case. [inference] Treat derived memories as personal data where their source is.

## What the evidence supports

### Measured with a disclosed protocol

These are often author-run but can be reproduced:

1. **Accuracy.** Even in vendor-run studies, memory layers beat full context on cost and latency (90%+ fewer tokens; seconds instead of tens of seconds), but not consistently on accuracy. Full context won Mem0's own 2025 LoCoMo run. Zep beat full context on LongMemEval_s, where histories of ~115k tokens degrade long-context reading.
2. **Destructive rewriting loses information.** ACE's collapse measurement, HaluMem's 5–62% correct-update rates, MemoryAgentBench's ≤28% on multi-hop selective forgetting, and Mem0's own retreat to ADD-only writes all point the same way.
3. **Lexical + dense hybrid retrieval with reranking reliably helps.** Evidence comes from Zep, Mem0 2026, LongMemEval's key and query expansion, IRPAPERS fusion, Blueprint, and the RAG-vs-GraphRAG comparison. Graph structure helps multi-hop questions and hurts detail questions.
4. **Experience memory improves agents when there is a success signal** (AWM, ReasoningBank, ACE, Dynamic Cheatsheet, AFTER). The gains are typically single- to low-double-digit points.
   - Stored errors propagate: agents copy similar past records (experience following).
   - Whether distilled rules or raw examples transfer better is contested (ReasoningBank and arXiv 2604.27003 versus SkillEvolBench).
5. **Drawing retrieval.** On drawing sheets, patch-level visual retrievers far exceed OCR-text retrieval (PlanSightRAG: 91–95% vs 37% R@5). Region and title-block OCR with BM25 wins for identifier queries (Blueprint), and fusion beats either alone (IRPAPERS). VLM grounding and symbol counting remain weak (ViDoRe V3 bounding-box F1 below 0.09; AECV-Bench counting 0.40–0.55).
6. **Memory poisoning is practical** against agents that write their own memories (MINJA 98% injection; MemoryGraft; WhisperBench 71–88% end-to-end). Defenses that rely on platform-held provenance, not LLM judgment, performed best in author harnesses.

### Vendor claims to treat as unverified

- Benchmark leadership claims: Mem0 92.5 / 94.4, Supermemory "#1" and 97% Recall@20, Hindsight 94.6, Agent Zero 95.6, MemOS "first in all categories", EverMemOS 94.5.
  - LoCoMo scores above the audited 93.57% ceiling indicate lenient judges.
  - A matched third-party run put Mem0 at 61.4% and Supermemory at 65.4%.
- Anthropic's +39% memory-plus-context-editing figure comes from an undisclosed internal evaluation.
- Graph memory "excels at temporal reasoning": the 2025 Mem0g gain was about 1.5 J overall.
- Model-card retrieval scores and AEC product capabilities (Bedrock, VitruAI) have not been independently evaluated.

## Open uncertainties

1. **No benchmark covers organizational, multi-user, visual or document-centric memory.** Every number in section 3 comes from personal chat history or agent tasks, so transfer to firm drawing-review practice is untested.
2. **Raw episodes versus distilled rules** for procedural knowledge such as reviewer corrections: the evidence conflicts, and nobody has measured corrections made by human experts rather than self-judged outcomes.
3. **Whether human approval of learned rules improves outcomes** has no controlled study. Trust thresholds and consensus filters may suppress rare but correct firm-specific practices; false-rejection rates are unreported.
4. **Image-to-image detail similarity** (a crop as the query, finding similar details from prior projects) has no benchmark. Generic encoders do poorly on drawing similarity, and how to tile and rasterize large sheets rests on one paper.
5. **Deletion through derived memories.** Zep explicitly does not regenerate shared summaries, and no vendor documents rebuilding consolidated rules after a source is deleted.
6. **2026 preprints.** Many results cited here are preprints without peer review or replication: True Memory, Agent Zero Memory, PlanSightRAG, GARRET, MemLineage, PPMF, WhisperBench, SkillEvolBench.
7. **Running the strongest open visual retrievers locally under Bun** is unverified: no official ONNX export exists for ColModernVBERT, ColQwen or Qwen3-VL-Embedding. Section 5 covers the text-embedding side.
